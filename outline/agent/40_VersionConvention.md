# Photogiraffe 版本号规范 (Version Convention)

> **生效日期**：2026-02-26（v0.19 起执行）  
> **大版本**：当前处于 `v0`（开发/早期阶段）

---

## 一、版本号结构

```
v{大版本}.{Phase}.{步骤}[.{修订}]
v  0  .  19  .  1  [.  1  ]
│     │       │         └─ 修订：bugfix / hotfix / security（可选）
│     │       └─────────── 步骤：Phase 内每个子版本（功能增量）
│     └─────────────────── Phase：大阶段编号（与历史 Phase N 对应）
└───────────────────────── 大版本：0 = 开发版，1 = 首个稳定发布
```

| 层级 | 含义 | 示例 |
|------|------|------|
| `v0` | 大版本（过渡到 v1 = 功能完整首发）| — |
| `v0.19` | Phase 19 全部内容交付 | 导出历史管理页 |
| `v0.19.1` | Phase 19 第 1 子步骤 | Go Core 端点 |
| `v0.19.1.1` | Phase 19 步骤 1 的 bugfix/hotfix | 修复某一 bug |

---

## 二、git commit 消息格式

```
{v0.X.Y[.Z]}: {简短描述}

{可选正文：详细变更说明}
```

**示例：**
```
v0.19.1: Go Core — GET /api/exports + DELETE /api/exports/:id

- 新增用户维度导出历史列表端点（分页，支持状态过滤）
- 新增删除导出记录端点（仅允许删除 completed/failed 状态）
```

```
v0.19.1.1: 修复导出记录删除时 MinIO 文件未清理

- DELETE /api/exports/:id 现在同步删除 MinIO exports/ 对象
```

## 三、版本号递增规则

| 场景 | 如何递增 | 示例 |
|------|---------|------|
| 新功能子步骤 | 步骤号 +1 | v0.19.1 → v0.19.2 |
| Phase 完成 | Phase 号 +1，步骤归零 | v0.19.N → v0.20.0 |
| Bugfix（当前 Phase）| 子版本 .1 递增 | v0.19.2 → v0.19.2.1 |
| 安全修复（任意时刻）| 在当前最新步骤追加修订号 | v0.21.3 → v0.21.3.1 |
| 重大重构（不改 Phase）| ─ | 不允许；升 Phase |

## 四、Tag 规范（可选，用于 GitHub releases）

```
git tag v0.19.0      # Phase 19 全部完成时打 tag
git tag v0.19.2.1    # 重要修复也打 tag
```

## 五、日志文件命名更新

日志文件继续使用现有格式：`YYYYMMDD_HHMMSS_vX.Y.md`
- Phase 步骤日志：`20260226_150000_v0.19.1.md`
- Hotfix 日志：`20260226_180000_v0.19.1.1.md`
