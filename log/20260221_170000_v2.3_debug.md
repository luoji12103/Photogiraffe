## 发现并修复的 Bug

### B1 — go-core：文件扩展名提取错误（`last-4-chars` 截取法）

**文件**：`go-core/main.go`  
**严重程度**：🟠 中危（影响 `.jpeg` / `.tiff` / `.webp` 等5字符扩展名）

**问题**：原代码使用 `file.Filename[len(file.Filename)-4:]` 截取扩展名，对于5字符扩展名（如 `.jpeg`）会得到 `"jpeg"`（缺少前导点），导致 MinIO 对象名为 `raw/uuid-xxxx.jpeg` 变成 `raw/uuid-xxxxjpeg`（无点分隔符，扩展名丢失）。

```go
// 修复前（错误）
ext := ".jpg"
if len(file.Filename) > 4 {
    ext = file.Filename[len(file.Filename)-4:]  // ".jpeg" → "jpeg" ❌
}
```

**修复**：改用标准库 `path/filepath` 的 `Ext()` 函数，正确处理任意长度扩展名。

```go
// 修复后（正确）
ext := filepath.Ext(file.Filename)  // ".jpeg" → ".jpeg" ✅
if ext == "" {
    ext = ".jpg"
}
```

### B2 — go-core：`AutoMigrate` 重复执行

**文件**：`go-core/main.go` + `go-core/database/db.go`  
**严重程度**：🟡 低危（功能无影响，仅增加启动耗时）

**问题**：`database.Connect()` 内部已执行一次 `AutoMigrate`，但 `main()` 函数中又显式执行了一次相同的迁移，造成每次启动时迁移运行两遍。

**修复**：删除 `main.go` 中多余的 `AutoMigrate` 调用，保留 `database.Connect()` 内的一次调用即可。

---

### B3 — go-core：EXIF 数据重复创建

**文件**：`go-core/main.go`（`PUT /internal/photos/:id/status` 处理函数）  
**严重程度**：🟠 中危（Worker 重试时会导致同一张照片存在多条 EXIF 记录）

**问题**：Python Worker 更新照片状态时，`ExifData` 每次都用 `database.DB.Create()` 写入，没有检查是否已存在相同 `photo_id` 的记录。当 Worker 崩溃重启后重试处理同一张照片，会导致数据库中出现重复 EXIF 行。`Preload("ExifData")` 使用 `has-one` 语义只返回第一条，后续记录永久孤立。

**修复**：先用 `First()` 查询 `photo_id` 是否已有 EXIF 记录：
- 无记录 → `Create()`（首次写入）
- 有记录 → 复制 `Model` 字段后 `Save()`（幂等更新）

### B4 — go-core：AI 分析未检查照片处理状态

**文件**：`go-core/main.go`（`POST /api/photos/:id/analyze`）  
**严重程度**：🔴 高危（可导致 Python Worker panic）

**问题**：`/api/photos/:id/analyze` 端点对照片状态无任何校验。如果对 `status = "failed"` 的照片触发 AI 分析，Worker 会尝试从 MinIO 下载 `proxy/` 路径的 WebP 图片，而该图片根本不存在（处理失败时没有产出 proxy 文件），Worker 会抛出 `NoSuchKey` 异常并标记该消息为未 ACK（永久挂起）。

**修复**：在 `analyze` 端点中加入状态前置检查：

```go
if photo.Status != "completed" {
    return c.Status(fiber.StatusBadRequest).JSON(fiber.Map{
        "error": "Photo processing is not complete yet...",
    })
}
```

### B5 — 前端 `PhotoDetail.tsx`：`setTimeout` 中陈旧闭包

**文件**：`frontend/src/components/PhotoDetail.tsx`  
**严重程度**：🟠 中危（AI 分析超时后用户无法获知失败原因）

**问题**：`handleAnalyze` 函数中，`setTimeout` 回调通过闭包引用了 `isAnalyzing` 状态值。由于 React 状态更新是异步的，`isAnalyzing` 在闭包中始终是调用 `handleAnalyze` 时那次渲染的旧值 `false`，导致超时后 `if (isAnalyzing)` 永远为假，"Analysis timed out" 错误信息从不显示。

```typescript
// 修复前（永远不会触发错误提示）
setTimeout(() => {
    clearInterval(pollInterval);
    if (isAnalyzing) {  // ← 始终为 false（陈旧闭包）
        setIsAnalyzing(false);
        setAnalysisError("Analysis timed out...");
    }
}, 60000);
```

**修复**：使用 `setIsAnalyzing` 的函数式更新形式，通过 React 调度器获取当前最新值：

```typescript
// 修复后（正确读取最新状态）
setTimeout(() => {
    clearInterval(pollInterval);
    setIsAnalyzing((wasAnalyzing) => {
        if (wasAnalyzing) {
            setAnalysisError("Analysis timed out. Please try again later.");
            return false;
        }
        return wasAnalyzing;
    });
}, 60000);
```

### B7 — go-core：`AIAnalysis` 空字符串插入 `jsonb` 列失败（关键 Bug）

**文件**：`go-core/models/models.go`、`go-core/main.go`  
**严重程度**：🔴 高危（**所有新照片上传均失败**）

**问题**：`Photo` 模型的 `AIAnalysis` 字段定义为 `string` 类型，GORM 在 `CREATE` 新记录时插入 Go 零值 `""`（空字符串）。PostgreSQL 的 `jsonb` 列类型拒绝空字符串，抛出：
```
ERROR: invalid input syntax for type json (SQLSTATE 22P02)
```
导致 `INSERT INTO photos ...` 失败，每次上传都返回 `{"error":"Failed to save photo metadata"}`。

**验证**：从 go-core 日志中直接观察到错误：
```
2026/02/21 16:46:57 Failed to create photo record: 
ERROR: invalid input syntax for type json (SQLSTATE 22P02)
... VALUES (...,'') -- ai_analysis = '' 是非法 jsonb
```

**修复**：将模型字段改为可空指针类型 `*string`，使 GORM 在无 AI 分析时写入 SQL `NULL`（合法的 `jsonb` null），而不是空字符串：

```go
// models.go
// 修复前
AIAnalysis string `gorm:"type:jsonb"`

// 修复后
AIAnalysis *string `gorm:"type:jsonb"` // nullable; NULL until AI analysis is completed
```

同步更新 `main.go` 中 AI 分析结果写回逻辑：
```go
// 修复前
photo.AIAnalysis = input.Analysis

// 修复后
photo.AIAnalysis = &input.Analysis  // 取地址符，适配 *string
```

同步更新前端 TypeScript 接口：
```typescript
// PhotoDetail.tsx Photo interface
AIAnalysis?: string | null;  // null when AI analysis not yet performed
```
